## 1. 기준층 DB화 (전체 참조 일원화)

### 현재 문제

PaymentStatus.jsx CONFIG 객체에 하드코딩 → 소스코드 수정 없이 변경 불가, 다른 화면에서 재사용 불가

### 해결: buildings 테이블에 두 컬럼 추가

```sql
ALTER TABLE buildings ADD COLUMN oiling_base_floor INTEGER DEFAULT 0;
ALTER TABLE buildings ADD COLUMN cleaning_base_floor INTEGER DEFAULT 0;

-- 갱폼 박리제 기준층 초기값
UPDATE buildings SET oiling_base_floor = 7 WHERE name IN ('1동', '2동');
UPDATE buildings SET oiling_base_floor = 3 WHERE name IN ('3동','4동','5동','6동','9동');
UPDATE buildings SET oiling_base_floor = 2 WHERE name IN ('7동', '8동');

-- 세대청소 기준층 초기값
UPDATE buildings SET cleaning_base_floor = 4 WHERE name IN ('1동', '2동');
UPDATE buildings SET cleaning_base_floor = 3 WHERE name IN ('3동','4동','5동','6동','9동');
UPDATE buildings SET cleaning_base_floor = 2 WHERE name IN ('7동', '8동');
```

### 영향 범위 (이번 구현 전체 포함)

| 화면/API | 변경 전 | 변경 후 |
|---------|--------|--------|
| PaymentStatus.jsx | CONFIG.limits 하드코딩 | API 응답 oiling_base_floor 참조 |
| MonthlyAnalysis (신규) | - | DB JOIN |
| RevenueProjection (신규) | - | DB JOIN |
| MasterManager 건물탭 | 기준층 입력 없음 | 갱폼/청소 기준층 입력 필드 추가 |
| /api/master/buildings | 기준층 미포함 | 두 컬럼 포함 반환 |

> **핵심**: PaymentStatus.jsx의 CONFIG.limits 하드코딩을 이번 작업에서 함께 제거합니다.

## 3. 신규 화면: 예상 수입 분석 (RevenueProjection)

### 갱폼 예상 수입 계산

```
예상 갱폼 수입 = Σ(동별 미완료 층 × 해당 층 세대수 × 단가)
미완료 층 = 기준층 초과 ~ 최고층 중 oiling_records가 없는 층
```

### 세대청소 예상 수입 계산

```
예상 청소 수입 = Σ(동별 미완료 청소 층 × 층 세대수 × 단가 × 잔여차수)
잔여차수 = 최대차수 - 이미 완료된 차수
```

### 화면 구조

```
[갱폼 예상 수입]
 동  | 기준층 | 최고층 | 완료층수 | 미완료층수 | 예상수입
 1동 |  7층   |  20층  |   4층   |    9층    | 2,664,000원
 2동 |  7층   |  25층  |   4층   |   14층    | 4,144,000원
 ...
 합계                                          XX,XXX,XXX원

[세대청소 예상 수입]
 동  | 대상층 | 완료층/차수 | 미완료 | 예상수입 ...

[통합 요약]
 현재 확정 수입: 6,438,000원
 잔여 예상 수입: XX,XXX,XXX원
 총 예상 수입:  XX,XXX,XXX원
```
